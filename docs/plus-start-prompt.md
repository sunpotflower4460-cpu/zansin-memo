## 1. 目指す体験

中心にしたいのは、「自分の考えが、目で見てわかりやすくなる」上質な地図です。Plusでは見やすさ・探しやすさ・整理しやすさ・元の場所へ戻りやすさが大きく向上し、AIを使わなくても購入する意味がある体験にしてください。

AIは、本人には見えていなかった関係を、原文と理由を添えて提案する役割です。正解を決めたり、本人の文章やつながりを勝手に変えたりしません。

アトリエでは、気になる材料を並べて、自分の言葉を育てられるようにします。作品集では、選んだ言葉や地図を、ことばカードや1ページの作品として残せるようにします。すべて任意の入口とし、静かに書ける今の体験を守ってください。

## 3. 守る体験とデータの境界

- 無料の記録、手動接続、基本地図、自分で書く芽、全件検索、書出し・削除を保ちます。無料版を意図的に不便にして有料版との差を作らないでください。
- 地図では確定した接続、AIの候補、表示上のまとまりを区別します。A–BとB–Cがあっても、A–Cの接続は作りません。保存した範囲・位置・選択を保ち、範囲外を一時的に見ても戻れるようにします。
- 「候補を見る」「接続を採用する」「材料にする」「下書きを保存する」「芽にする」「作品に残す」「外へ共有する」は別の操作です。閲覧や材料選択だけで接続や芽を確定しません。件数や日数を条件に自動で芽へ昇格させません。
- 原文と、本人の下書き・選んだ版・芽・作品を分けます。アトリエの版から、芽にせず直接作品へ残せます。「作ったときの材料」と「現在の原文」を区別し、原文を見て戻っても開いていた作品の版を保ちます。
- AIは本人が選んだ範囲と確認した送信内容だけを扱います。購入と送信同意を分け、送信しない選択でも地図・アトリエ・作品集のローカル機能を使えるようにします。APIキーや秘密情報をアプリ・ログ・リポジトリへ入れません。
- 送信中の原文変更・削除・同意撤回で古いAI結果を採用しません。引用の根拠を照合し、結果がない時や失敗した時に、無理に候補を作りません。利用枠は再試行・遅延応答で二重に消費させません。
- 課金が切れても、自分の文章や既存作品を閉じ込めません。既存作品の閲覧・基本編集・保存済みの形式と配置でのPNG/PDF再出力を保ちます。詳細は利用権表に従ってください。

## 4. 実装の順序と最初の範囲

全体の目標はPhase 11.0〜11.6です。各Phaseをレビューできる小さな変更へ分け、対象・対象外・完了条件を短く示してから進めてください。

1. 11.0：保存・移行・データ契約・技術検証。
2. 11.1：地図の品質、全体と周辺、まとまり、検索、位置保持、保存した見方。
3. 11.2：原文と理由を持つAI提案、個別採用、送信同意、取消、利用枠。
4. 11.3：材料棚、下書き、案と版の比較、固定した一節、芽への明示的な採用。
5. 11.4：ことばカードと地図・文章の1ページ、作品から材料への往復、実ファイル出力。
6. 11.5：購入・復元・失効等の状態と、利用者のデータ権利。
7. 11.6：無料とPlusの一周、実機、アクセシビリティ、AI品質、購入、出力品質の検証。

最初のPRは11.0の一つのまとまりに絞ってください。候補は、保存量の技術検証、追加契約と純粋な検証関数、起動・移行の判定を確認する最小の変更です。6画面、保存先の切替、購入SDK、バックエンドを一度に入れないでください。

保存は、v3の通常起動・移行途中・旧版フェンス・破損・全削除を設計どおりに扱ってください。単一writerを、全履歴を毎回一つの巨大JSONへ書く義務と考えず、件数と保存総量の両方を測って方式を決めてください。本番の保存形式を有効化する前に、復旧と実機性能の条件を満たしてください。

最初のPRや計画書の作成だけで全体を完了扱いにせず、完了した範囲を記録し、依頼済みの次の範囲へ進めてください。複数ページ冊子、クラウド同期、共同編集、別の課金プランは初回の範囲に追加しません。

## 5. 未決事項がある時の進め方

価格、試用、AI利用枠、モデル、購入SDKなどは未確定です。仮の値を本番仕様として固定せず、必要な一次資料・互換性・原価・検証結果をもとに、判断が必要な項目を記録してください。

外部設定や資格情報が不足していても、独立したローカル機能、型、アダプター、開発用の模擬状態、検証は進めてください。実際のAI・購入・実機が必要な部分だけを未完了として残します。模擬機能を、本物のAIや購入が使える機能として利用者に表示しないでください。

必要な設定や確認を依頼する時は、先に進められる作業を終えたうえで、何が必要で、どの機能・検証が待っているかを具体的に示してください。

## 6. 品質の確認

コード変更時はnpm run checkを実行し、変更した契約と残るリスクに必要な検証を追加してください。移行・保存失敗・重複操作・遅延応答・同意撤回など、実際にデータや利用枠を守る検証を優先してください。

地図の品質は外観だけで判断しません。同じデータと端末で「関係を把握する」「材料を探す」「原文や制作画面から同じ場所へ戻る」を無料版とPlusで比べ、操作数、読み違い、戻り失敗、本人が説明できる便利さを記録してください。比較手順と合格条件は地図設計に従い、複数の課題で改善を確かめてください。

実装済み、Node/Webで確認済み、実iPhoneで確認済み、実AI・Sandboxで確認済み、販売可能を分けて報告してください。固定のAI例をモデル品質、模擬購入をStoreKitの検証、Web表示をVoiceOver実機確認の代わりにしないでください。未実施の受入例を合格扱いにしません。

## 7. 変更の保存と完了報告

既存の作業を尊重して作業ブランチを使い、小さくcommitしてください。利用可能な接続で、そのブランチへのpushとdraft PR作成まで進めて構いません。既存の変更を消すresetやforce pushはしないでください。

この依頼の範囲は実装・検証・レビュー可能な形での保存です。本番へのmerge、外部サービスの本番有効化、実メモの外部AI送信、ストア申請・販売開始は、その時点のユーザー指示と既にある許可範囲で判断してください。許可済みの作業について再確認を繰り返す必要はありません。

docs/plus-implementation-plan.mdの進捗・検証記録を更新し、最後に次をやさしい日本語で報告してください。

- 利用者にとって、何ができるようになったか。
- 完了したPhaseと、変更した主なファイル、commitまたはPR。
- 実際に行った確認、その環境と結果。
- 未実装・未検証・外部設定待ちの範囲と、販売前に残る条件。
- 次に進める具体的な作業。

まず最新のリポジトリと設計を確認し、最初の小さな変更の範囲を示して、実装に着手してください。
