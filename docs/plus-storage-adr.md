# Phase 11.0 — Plusの保存方式を選ぶための計測

2026-11-27（日本時間）。`main` の `22750af` を基準とした初回の技術検証。

## 判断

開発検証には、一つのJSONを確定点とする方式を使う。本番の方式は実iPhoneの計測と障害試験を待つ。正本の更新は一つのwriterが順番に受け持つ。実機で全体書込みが基準を満たせない場合は、版と引用を個別保存し、小さいmanifestに参照を確定する方式を比較する。履歴の件数上限や自動削除は設けない。

## 再実行

```sh
npm run measure:plus-storage -- sizes
npm run measure:plus-storage -- light
npm run measure:plus-storage -- heavy
```

Linux x86_64、Node 24.22.3、一時ディレクトリのoverlayfsで計測。文字列はすべて架空。種の約1割を長文、約4分の1を未接続とし、最大300本の接続を持つ種を置いた。1アトリエにつき異なる2,000字の節目版20件と、25ノードの作品地図1件を用意した。作品地図は位置、ラベル、実接続の両端と理由を含む。材料は共有するものと異なるものを混ぜた。

| 種 | 接続 | 1アトリエ・1作品（UTF-8 byte） | 100アトリエ・100作品（UTF-8 byte） |
|---:|---:|---:|---:|
| 50 | 138 | 266,339 | 15,821,138 |
| 500 | 1,416 | 994,790 | 16,934,337 |
| 2,000 | 4,791 | 3,277,878 | 20,258,221 |
| 5,000 | 11,541 | 7,862,078 | 25,675,031 |

60秒にわたり500msごとに同じ下書きを1回更新した。毎回JSON全体を一時ファイルへ書いて正本へrenameし、最後に再読込して確定した内容を照合した。入力遅延は、予定時刻からイベントループが動くまでの時間。iOSのAsyncStorage、fsync、入力描画、IMEは未計測。

| 計測項目 | 50種・1アトリエ | 5,000種・100アトリエ |
|---|---:|---:|
| JSON化 p50 / p95 | 1.2 / 3.3 ms | 45.2 / 66.6 ms |
| 主保存I/O p50 / p95 | 1.4 / 3.0 ms | 47.1 / 101.9 ms |
| 入力から主保存の確定 p50 / p95 | 2.9 / 6.6 ms | 95.4 / 151.2 ms |
| 入力タイマー遅延 p95 | 2.8 ms | 2.2 ms |
| 同時に待つ保存の最大数（処理中を含む） | 1 | 1 |
| 停止後のflush / 再読込 | 2.2 / 2.7 ms | 113.3 / 124.6 ms |
| 保存中のサンプルで最大のJSヒープ | 11,231,304 byte | 101,880,824 byte |
| 再読込前までの最大RSS | 50,736 KiB | 288,688 KiB |
| 完了した主保存と照合 | 120回。最後の下書きを含む全文が一致 | 120回。最後の下書きを含む全文が一致 |

重い条件では、節目版・作品版・材料スナップショットだけで約17.3MBを占めた。書込み待ちの蓄積はこの条件では観測しなかった。JSヒープとRSSの増分が大きく、実機計測では入力・描画との同時実行も確認する。

## 保存と復旧の条件

| 観点 | 全体書込み | 版・引用とmanifestを分ける場合 |
|---|---|---|
| 確定点 | 検証した全体の主保存。lastGoodを補助にする | 版・引用の書込みと再読込を済ませ、参照が揃ったmanifestを主保存に確定する |
| 途中終了・容量不足 | 主保存の照合まで後続の更新を待たせ、入力と再試行用のIDを保持する | manifest確定前の参照先は未確定として扱う。確定済みの主保存とlastGoodの参照先を優先して保護する |
| 破損・旧版 | 破損の記録を保持し、同じ版のlastGoodから回復する。v3の痕跡があれば回復待ちへ進む | manifestと全参照を組で検証する。不足参照を空として確定しない |
| 回収・全削除 | 全削除markerで主保存、控え、旧原本と退避、途中データを除去する | 主保存・lastGood・移行が参照する版を平常時の回収から保護する。全削除では未参照領域も除去する |
| 持ち帰り | 版と由来を含む全データJSONを構成する | manifestが参照する版を読み、同じ意味の全データJSONを構成する。復元機能は別に検証する |

実iPhoneでは、同じfixtureを専用の開発ビルドで使う。機種、iOS、ビルド、保存先、容量を記録し、軽い条件と重い条件で各3回以上、500ms間隔で60秒入力する。主保存p95 500ms以内、入力描画p95 100ms以内、停止後のflush 2秒以内を暫定の目安とする。保存中の地図移動、強制終了後の復元、容量不足、ピークメモリも確認する。専用ビルドと実機での測定は未実施。

## 保存計測を実行できる開発画面

2026-11-27に、同じfixtureを使う計測画面を追加した。開発用フラグ `EXPO_PUBLIC_KIZASHI_PLUS_STORAGE_MEASURE=1` で起動する。実iPhoneではXcodeのあるmacOSで、端末を接続して起動する。

```sh
EXPO_PUBLIC_KIZASHI_PLUS_STORAGE_MEASURE=1 npx expo run:ios --device
```

「軽い条件で計測」と「重い条件で計測」は、それぞれ50件と5,000件の架空メモを一から用意する。実際のv3 writerと下書き保存を通して、正本と控えを更新する。結果にはUTF-8の保存量、JSON化、主保存、確定までのp50/p95、待ち件数、flush、読込時間、正本・控えと最終下書きの一致を含める。再起動後に「最後の保存を読み直す」で件数と下書きの更新回数を照合できる。ネイティブは専用キーのAsyncStorage、Webはタブ専用領域を使う。

端末では機種とOS、開発ビルドのcommit、空き容量、各試行のJSONを記録する。計測中の中断と再起動後の読込、容量不足による失敗を試す。入力の表示遅延、地図との同時操作、ピークメモリは画面操作とプロファイラーで別に測る。計測画面のJSタイマー遅延は、この入力描画の値に使わない。

Linux x86_64、Chromium 156のタブ専用領域で2回実行。50件（266,339 UTF-8 byte）は両方で120回を正本へ確定し、控えと全文を照合できた。最終試行のp95はJSON化3.8ms、主保存5.8ms、入力時点から確定まで9.9ms、JSタイマー遅延1.6ms。最大待ち件数は処理中を含め1件、flushは9.5ms、`loadGardenV3` は22.1msだった。5,000件（25,675,031 UTF-8 byte）は、初回の主保存を `QuotaExceededError` で拒否した。軽い条件の最終下書きは読込し直しても残り、通常版とPlusプレビューの記録は影響を受けなかった。

iOS・Android向けにこの画面を含む開発用JS bundleを生成した。実機AsyncStorageでの容量・速度・復旧は未計測。本番の保存方式を決める条件は引き続き保留する。
